# TheBrain Local API — endpoint map

Source: `http://localhost:11522/api/v1/docs.json` (OpenAPI 3.0.1, `TheBrain Local API v1.0`),
as served by TheBrain 15.0.640.
A copy of the spec: [`thebrain-local-api.openapi.json`](./thebrain-local-api.openapi.json).

- Base: `http://localhost:11522`; builds from before the port moved listen on `http://localhost:8001` (L15)
- Auth: `Authorization: Bearer <apiKey>`; the key lives in the desktop app under **Settings > User > Local API Key**
- Total: **48 paths**, 29 schemas, 9 tags
- The local API ≈ the cloud API plus a unique **App Control** group (`/api/app/*`)

## 3. Thoughts (13) — the core

| Method | Path | What it does |
|---|---|---|
| GET | `/api/thoughts/{brainId}/{thoughtId}` | Thought details (`ThoughtDto`) |
| PATCH | `/api/thoughts/{brainId}/{thoughtId}` | Update via **JSON Patch** (`name`, `label`, `aliases`, `typeId`, colours, `acType`, `kind`). A value is cleared with `remove`, never with `null`, and a type not at all (L19). A name of white space alone is a 200 that changes nothing, and a name is stored without the white space at its ends and cut at 1,024 UTF-16 units (L36) |
| DELETE | `/api/thoughts/{brainId}/{thoughtId}` | Delete a thought |
| POST | `/api/thoughts/{brainId}` | Create a thought (`ThoughtCreateModel`) → `{id}`. As the child of a type it is made one of that type, with no parent (L24). `relation` is 1, 2 or 3 and has no default: with 4, the spec's Sibling, or with none, the thought is linked to nothing (L25). A `sourceThoughtId` nobody has is a 404, one deleted a moment ago a 400, and neither makes a thought (L26). One of zeros is a 200 and a thought linked to nothing, and a `typeId` of zeros a 200 and a thought with no type (L29). A `name` of white space alone is a 400, and a longer one than 1,024 UTF-16 units is cut with a 200 (L36). With `kind: 4` under the name of a tag that is there, matched loosely, it makes nothing and answers with that tag's identifier; a type is made again under any name (L39) |
| GET | `/api/thoughts/{brainId}?nameExact=` | The first thought whose name matches exactly: to the letter case, and the newer of two. Answered from the search's index, so about five seconds behind a create, a rename and a delete: it returns a thought that is gone (L34) |
| GET | `/api/thoughts/{brainId}/{thoughtId}/graph` | **Thought + parents/children/jumps/siblings/tags/type/links/attachments**; `includeSiblings`. A thought stands in one list: a sibling that is also a parent, a child or a jump is not among `siblings` (L40). Answered from a copy once it has been read, behind a create by 0.2 s as a rule and by more than 0.3 s now and then, with no bound (L27, L33) |
| GET | `/api/thoughts/{brainId}/{thoughtId}/attachments` | A thought's attachments |
| POST | `/api/thoughts/{brainId}/{thoughtId}/pin` | Pin |
| DELETE | `/api/thoughts/{brainId}/{thoughtId}/pin` | Unpin |
| GET | `/api/thoughts/{brainId}/pins` | Pinned thoughts. A 400 when there are none (L1) |
| GET | `/api/thoughts/{brainId}/types` | All of the brain's Types (also thoughts, with `kind=2`). A 400 when there are none (L1). A copy: a new type is listed up to 0.42 s after its create (L39). A type reads with a `label` nobody gave it: its name, or the name it had when it became a type (L38) |
| GET | `/api/thoughts/{brainId}/tags` | All of the brain's Tags (`kind=4`). A 400 when there are none (L1). A copy, as `/types` is (L39) |
| GET | `/api/thoughts/{brainId}/{thoughtId}/modifications` | A thought's history; `maxLogs` and `includeRelatedLogs` are **both required** |

> Routing trap: `/api/thoughts/{brainId}/{thoughtId}` has the same shape as
> `/api/thoughts/{brainId}/pins|types|tags`. Literal segments win — never pass
> those words as identifiers.

## 4. Links (6)

| Method | Path | What it does |
|---|---|---|
| POST | `/api/links/{brainId}` | Create a link (`LinkCreateModel`: `thoughtIdA`, `thoughtIdB`, `relation`, `name`) → `{id}`. A parent/child link with a type above sets the lower thought's type (L21, L24), with a tag above attaches the tag (L23). `relation` is 1, 2 or 3: 4, the spec's Sibling, is a 400, and so is leaving it out (L25). Posted over the link a pair has, it answers that link's identifier and logs a `402`; two posted at once for one pair are usually two links (L35). Posted over with another relation, the link is rewritten to it under its identifier, its label, colour, thickness and direction kept. Between two thoughts joined by more than one link, any post is the 400 `"Link could not be created."` (L43) |
| GET | `/api/links/{brainId}/{linkId}` | Link details. Behind a patch (L22) and a deletion (L43) |
| PATCH | `/api/links/{brainId}/{linkId}` | Update via JSON Patch (`name`, `color`, `thickness`, `direction`, `relation`). Only a name and a colour can be cleared, with `remove`; `thickness` reads back a hundred times what was written (L22). A name is stored as a thought's is, with a tab and a line feed as spaces, no white space at its ends and cut at 1,024 UTF-16 units, and one the link has already logs nothing (L35). `kind` is the link's own and not what the link means: see *Tags* below |
| DELETE | `/api/links/{brainId}/{linkId}` | Delete a link: a 200 with no body, and a `102` in the log. A link that is gone, and an identifier no link has, is a 400 `Bad Request` with no other words (L43) |
| GET | `/api/links/{brainId}/{thoughtIdA}/{thoughtIdB}` | The link between two thoughts (404 if none). Not behind a write, a deletion included. A 404 as well for a pair that has two links the same way (L35); of two that go each way, the one whose `thoughtIdA` is named first (L43) |
| GET | `/api/links/{brainId}/{linkId}/attachments` | A link's attachments |

> Same trap: `/{linkId}` (2 segments) versus `/{thoughtIdA}/{thoughtIdB}`
> (3 segments) — they differ only in segment count.

## 7. Search (3)

| Method | Path | What it does |
|---|---|---|
| GET | `/api/search/{brainId}` | Search within one brain |
| GET | `/api/search/accessible` | Search across all accessible brains |
| GET | `/api/search/public` | Search public brains; supports `excludeBrainIds` |

Shared parameters: `queryText` (**required**), `maxResults` (**required**),
`onlySearchThoughtNames`.
⚠️ New content is not found at once: a new thought was first returned **3.7 to
5.5 s** after its create, at the next refresh of the search's index (13 runs,
L34). The vendor's documentation says "up to 15 seconds", which was not once
seen. This matters for the "create it, then immediately search for it" scenario.
A query is refused for its size without a word about size: a 414 with no body
past 8,192 bytes of request line, the catch-all 403 for 513 to 1,024 words
(measured, L30).
⚠️ The search of one brain answers from an index of its own, refreshed about
every five seconds, and **a hit is that index's copy of a thought**. Until the
next refresh it returns a thought that was deleted, and a changed one by its
old text and under its old name; a deleted thought now and then stays in it
for good. Nothing in a hit says so. `?nameExact=` (§3) answers from the same
index; `search/accessible` did not return a deleted thought (measured once and
not repeated by any test, L34).

## Data model

**ThoughtDto** — `id`, `brainId`, `name`, `cleanedUpName`, `label`, `aliases`, `typeId`, `kind`, `acType`,
`foregroundColor`, `backgroundColor`, `creationDateTime`, `modificationDateTime`,
`forgottenDateTime`, `linksModificationDateTime`, `displayModificationDateTime`.
A thought carries its `label` in its own read, in every list of a graph and
in `/types` and `/tags` (contract test): a read result prints it, as it prints
the `kind`, with no request of its own.

**LinkDto** — `id`, `thoughtIdA`, `thoughtIdB`, `relation`, `direction`, `meaning`, `kind`,
`name`, `typeId`, `color`, `thickness`.

**ThoughtGraphDto** — `activeThought`, `parents[]`, `children[]`, `jumps[]`, `siblings[]`,
`tags[]`, `type`, `links[]`, `attachments[]`. The fattest and most useful response
in the API.

**AttachmentDto** — `id`, `sourceId`, `sourceType`, `type`, `name`, `location`, `dataLength`,
`isNotes`, `position`.

**SearchResultDto** — `sourceThought`, `sourceLink`, `searchResultType`, `entityType`,
`attachmentId`, `brainId`/`brainName`, `isFromOtherBrain`. From the search within
one brain the last three are zeros, `null` and `false` (L6).

### Enumerations

| Enum | Values |
|---|---|
| `kind` (thought) | 1 Normal, 2 Type, 3 Event, 4 Tag, 5 System |
| `kind` (link) | 1 on every link read. The spec gives it as an integer and no values. A `PATCH` takes 1, and 2 only of a link with a `typeId`, where it is not kept (*Tags*, below) |
| `acType` | 0 Public, 1 Private |
| `relation` | 1 Child, 2 Parent, 3 Jump. The spec lists 4 Sibling as well, and nothing is written with it (L25) |
| `AttachmentType` | 2 ExternalFile, 3 ExternalUrl, 8 ExternalDirectory (the rest of `[0..15, 100]` are undocumented) |
| `EntityType` | -1 Unknown, 1 Brain, 2 Thought, 3 Link, 4 Attachment, 5 BrainSetting, 6 BrainAccessEntry, 7 CalendarEvent, 8 FieldInstance, 9 FieldDefinition |
| `ModificationType` | 101–105 generic (Created/Deleted/ChangedName/CreatedByPaste/ModifiedByPaste); 201–211 thought+link (colour, label, type, icons, fields, aliases); 301–304 thought (Forgot/Remembered/AccessType/Kind); 401–405 link (thickness/moved/direction/meaning/relation); 501–503 attachment; 601–602 brain; 701 access; 801–812 notes and assets; 900–903 calendar; 1001–1003 field definitions; 1101–1102 are in the enum with no description |
| `AccessType` | `[0,1,2,3,4]` — names not given in the spec |
| `SearchResultType` | `[0..7]` — names not given in the spec |
| `OperationType` (JSON Patch) | `[0..6]` — add/remove/replace/move/copy/test/invalid |

## Implications for tool scope

**The genuinely useful surface is 4 groups, roughly 30 endpoints.** The other 11
FileDownload paths plus BrainAccess/Users need no wrapper.

**Core (must have)**
- Search: `search/{brainId}`, `search/accessible`
- Graph reads: `thoughts/{brainId}/{thoughtId}/graph` — one call gives almost all
  of a thought's context
- Notes: read (markdown) plus `update`/`append`
- Writes: create thought, create link, PATCH thought/link

**App Control (the local API's killer feature)**
- `app/state` — where the user currently is, including which brain is open
- `activate` — the agent can highlight a result directly in the UI

**Valuable supporting endpoints**
- `thoughts/{brainId}/types` and `/tags` — the vocabulary needed for correct
  `typeId` values and tagging
- `attachments/by-location` — deduplication when saving links
- `modifications` (brain and thought) — "what changed since", for digests

### Things to account for when designing tools

1. **JSON Patch in the PATCH endpoints.** `ThoughtDtoJsonPatchDocument` is the raw
   operation format. That is a poor interface for an LLM: a tool should take flat
   fields (`name`, `label`, `color`) and assemble
   `[{op:"replace", path:"/name", value:...}]` internally.
2. **`brainId` everywhere.** `app/state` can supply a default, which is tempting.
   This project deliberately does not use it: writing into whichever brain the
   user happens to have open is the worst available failure. `brainId` is a
   required argument on every tool.
3. **No pagination.** Search takes `maxResults` (required), modifications takes
   `maxLogs` (required). Pick sensible defaults, or the model will invent them.
   The log can still be read in full by paging back on `endTime` (L14).
4. **No batch operations.** Creating a tree of N thoughts costs N+ calls — a
   candidate for a composite tool.
5. **Writes are not immediately visible.** "Create it and immediately find it"
   works through neither full-text search nor `nameExact`: both answer from
   an index refreshed about every five seconds (3.7–5.6 s, measured). Only reads by identifier are instant. Inside a batch write,
   link through returned UUIDs — see L12.
6. **No "list all thoughts" endpoint** and no traversal deeper than one hop —
   only `graph` for a single thought. Breadth-first traversal has to be built.
7. **No API for fields, calendar events, icons or brain settings** — even though
   `ModificationType` knows about them. They can only be observed indirectly
   through the modification log.
8. **Destructive operations**: DELETE brain / thought / link / attachment, and
   POST notes `update` (which replaces the whole note). These need to be marked
   or hidden behind a flag.
9. **Responses are content-negotiated** as `text/plain` / `application/json` /
   `text/json` — send `Accept: application/json` explicitly.

### Divergences from the spec, and bugs

| # | Observation | Consequence for MCP |
|---|---|---|
| L1 | **`/types`, `/tags` and `/pins` return `HTTP 400` when the list is empty, in the words of a failure.** Each answers a bare JSON string with the brain's identifier at its end: `"Could not retrieve list of Types for brain <id>"`, `"Could not retrieve list of Tags for brain <id>"`, `"Failed to get pins for brain <id>"`. With one type, tag or pin the same request is a 200 and a list, and the 400 is back at the first read after the last one is deleted, 2 to 3 ms after. No 200 was seen with an empty list. 5 of 5 for each, the pins of a brain taken off and put back. **What a failure answers** is told apart by its status, for every failure that could be produced: a `brainId` that is no brain is the 401 of L3, a rejected key the other 401, a malformed identifier the HTML page of L2. No request of the three could be made to fail with a 400, so whether the API has another sentence for a list it could not read is not known: the one it has names no cause. Measured on 15.0.640, 2026-10-13 | `emptyOn400()` takes those three sentences for an empty list, and no other 400. It took any 400, so a request refused for a reason of its own read as a brain with no types, and `brain_list_types_and_tags` answered "This brain has no types or tags yet". **Known limit:** a list the API could not read, told in the same sentence, would still be taken for empty. And should a later build word the empty list differently, a brain with none is an error in the API's words until the pattern follows: the contract test says so first |
| L2 | **A malformed UUID in the path → HTTP 200 plus the Blazor app's HTML page.** The route does not match and the request falls through to the SPA fallback. That is a `GET`, with the bad identifier in a thought's place or the brain's (7 paths, 5 of 5 each), and a `GET` of a path the API does not have answers the same. A `PATCH`, a `DELETE` and a `POST` with one are a 400 with an empty body (4 paths, 5 of 5 each). A well-formed identifier nobody has never gets the page (L3) | A naive client takes 200 for success and chokes on HTML. Validate UUIDs before the request and check the response `Content-Type` |
| L3 | **An identifier nobody has is answered by each request in its own way, and a `brainId` that is no brain by a 401 that reads like a key's.** For a well-formed UUID that no thought of the brain has: `GET /api/thoughts/{brainId}/{id}` and a `PATCH` of it are a 404, a ProblemDetails that says only `"Not Found"`; its `graph` is a 403 with the router's text, "To use the TheBrain API, make requests to /api…"; its `attachments` and `modifications` are a 200 with an empty list, and `GET /api/notes/…` a 200 with the "no note" sentinel; a `DELETE` of it is a 200 that deletes nothing. The all-zero GUID, the identifier of a link or of the brain, a thought deleted earlier and a thought of another brain read through this one are answered like any identifier nobody has. **The 403 is the API's catch-all and says nothing of access.** It names no cause, and it is also what a patch the API cannot apply gets (L19, L21, L22), and the read of a note for up to 0.3 s after its attachment is deleted (12 of 12, six of them on a thought that is there). **A `brainId` no brain has** is a 401 `"Access to brain <id> is unauthorized."` from every request with a brain in its path, a read or a write, whatever else it names: 56 kinds of request, 810 sent. A rejected key is the other 401, `Invalid API Key`, and the key is asked about first. Each answer was the same every time it was asked for; the requests and the counts are in *An identifier nobody has, and a brain that is not there* below. Measured on 15.0.640 | The client tells the two 401s apart: `unknown_brain` for the brain, `auth` for the key. The tools used to answer a wrong `brainId` with "TheBrain rejected the key", and `brain_search` with an empty result. `describeError()` now says it is `brainId`, that the key was accepted and the other identifiers not looked at, and points at `brain_list`; `brain_search` passes that refusal on. For a 404 it keeps the API's words where they name the identifier, and where they do not it names the thought or the link the request's path addressed. For the 403 it says that no cause was given, names the request, and no longer says "Access denied". None of the three mentions `brainId`. The 400 a link gets for an end nobody has is told as the 404 is, the API's words kept and the request left out (L35). The reads that decide a kind (`requireType`, `requireTag`, `requireParent`) take only the read's own 404 for "no such thought": a 403 taken for one would call a type that is there no type, and let a type through as a parent. **A tag taken off a thought nobody has** was answered "was not on the thought", in a result that was no error (3 of 3): the lookup of a link is the same 404 for such a thought as for two thoughts with no link. `brain_tag` now reads the thought before it gives that answer, once a call, and passes the read's 404 on; a removal that finds its tag reads nothing more. **Not guarded.** A note written to an identifier nobody has is reported as written by `brain_set_note` and `brain_append_note`. A parent nobody has is left to the write by `brain_create_thought` and `brain_link`, whose first write it is; a plan that names one is rejected ahead of its writes (L26). The 403 cannot be told from a request that failed for a reason of its own, so its message says what it most often means and no more. **For the read of a note it is never an identifier nobody has**, which that read answers with a 200: the tools that read a note take the 403 for a read that failed, never for a thought with no note, and its message says what it is (*A note whose attachment was deleted a moment ago*, below) |
| L4 | **`notes/append` on a thought with no note is a silent no-op**: HTTP 200, the note stays empty | An append tool must read the note first and fall back to `update` when there is none |
| L5 | **A code block that is closed reads back to the character. What a note loses is a line that begins with ` ``` ` and has no partner, and a block with nothing in it.** This row said that a Markdown round trip loses the closing ` ``` ` of a code fence, "with the rest of the document swallowed into the block". It came with the first commit, from a TheBrain 15 on port 8001 whose build was not written down, and never had a contract test; the tools warned of it under every note with a fence. **What is stored**, by `POST …/update` and by `…/append`, each with a 200: the text as it was sent, with `\r\n` as `\n`, less the lines of two rules. Both go by the lines that begin with three backticks at the very start of the line, whatever follows them there: a language, more backticks, or a sentence that opens with a code span. *An odd one out:* with an odd number of such lines the last is deleted, whole. *Nothing in it:* the rest pair up in order, and a pair with no line between, closed by a line that is three backticks and nothing else, is deleted, both lines. A fence that is indented, in a list item or in a quote is not counted, nor one of tildes, nor one after a carriage return alone. So a block left open loses the fence that opened it; a block whose first fence is not at the start of its line loses the one that closes it; a line of prose that opens with a triple-backtick code span goes with its sentence; and a fence of four backticks around a bare one loses its first two lines. A text that comes to nothing this way leaves no note, and deletes the one that was there. Nothing else is touched: a carriage return alone, blank lines and blanks at either end, a byte order mark and raw HTML come back as sent, and the file behind the note, `Notes.md`, is a byte order mark and the text that is read. **`append` is gone over as the whole note**, not as the text added, and joins that text to the note's last line: a closed block appended straight after the note's last line has its first fence joined to that line, and loses its closing fence, 60 of 60, after text and after a note that ends in a fence. That is this row's old claim, and the one way found to see it. With a line end between the block is kept, 100 of 100, 40 of them with the blank line `notes.append()` puts there. **Counts**, the cases and the other two forms a note is read in: *A note's Markdown* below. **Not measured:** what the app's editor writes when a person edits a note, and any other build. Measured on 15.0.640, 2026-10-13 | `noteAsStored()` is the rule and `noteLinesDropped()` the lines it takes, by number. **The tools warn of a note that lost a line, and of no other**: `brain_set_note`, `brain_append_note`, `brain_create_thought` and `brain_ingest` name each line by its number in the text and by what it held, give the two rules, and say to write the note again. The warning for every fenced note is gone, with its advice to indent code instead. A note is written as it was given: nothing is refused and nothing mended, since what a line was meant for is the caller's to say. `brain_append_note` counts in the whole note, which `notes.append()` returns as it sent it: where the note already holds a fence with no partner, a closed block added to it is what loses a line. `ingest()` sets a plan's note against the note a thought has as it would be stored (L33): a note with a fence left open read as "another text" on the run after the one that wrote it |

### Aliases — what could not be measured

L16 is measured on 15.0.640 and each claim in it has a contract test. Two things
about aliases are not, and are taken on trust:

- **The version requirement.** The spec says: "Saving the first alias in a brain
  makes the brain require TheBrain 15.0.621 or later on every device." Checking
  it would take a second device on an older build. The tools repeat it on every
  argument that can write an alias.
- **Builds before 15.0.621.** They have no aliases, so a thought arrives without
  the field, and reads treat that as an empty list. What such a build does with
  `aliases` in a create request is unknown; a field ignored in silence would be
  reported as written. So before sending aliases the client reads the brain's
  home thought, and refuses when the field is absent.

### Tags — the undocumented mechanism

`LinkDto`'s **`meaning`** field discriminates the kind of link. The spec says only
`integer` and describes no values. Found empirically:

| `meaning` | What the link is |
|---|---|
| 1 | ordinary (child / parent / jump) |
| 2 | a type binding (created by `PATCH /typeId`) |
| 3 | a type bound to another type: the log's `TypeOf` (L44) |
| 5 | a tag binding |
| 7 | a tag bound to another tag (L23, L44) |

The field is **read-only**: `PATCH /meaning` returns 200 and silently ignores the
value, whichever of 1, 2, 5 and 7 is sent, on a jump, a child's link, a type's
and a tag's. The server sets it, inferring from the `kind` of the target thought.

**A link's `kind` is not its `meaning`, and patching it is no way to it.** This
paragraph used to end "`PATCH /kind` returns 400 `"Invalid 'kind' specified."`",
which is what one value gets; what `PATCH /kind` does to a *thought* is row L31.
A link has a `kind` of its own, 1 on every link read, which the spec gives as
an integer with no values. `PATCH /api/links/{brainId}/{linkId}` with `replace` on `/kind`, sent to a
link with no `typeId`:

| Value | Answer |
|---|---|
| 1, or `"1"` | 200. The link reads a `typeId` of zeros from then on, where it read `null` (11 of 12; once the read 0.3 s later still had `null`) |
| 2, or `"2"` | 400 `"Link 'typeId' must be specified if setting 'kind' to '2'."` |
| -1, 0, 3, 4, 5, 6, 99 | 400 `"Invalid 'kind' specified."` |
| `null`, 1.5, `"tag"`, `true` | the catch-all 403 of L3 |
| `remove`, `add` | 400 `"Only 'replace' operations are allowed for 'kind' path."` |

To a link that has a `typeId`, the zeros a `kind` of 1 leaves for one, 2 is a
200: the link reads `kind: 2` at once and `kind: 1` again 22–344 ms later, and
`statistics.linkTypes` stays 0 (18 of 18, six each with a `typeId` of zeros, of
another link and of nobody). Nothing is kept. `PATCH /typeId` on a link takes any
identifier with a 200 and logs a `203` with no values; `remove` there is a 200
that leaves it, and `null` a 400 `"Link typeId not specified."` (3 of 3 each).
Through all of it the link's `meaning` and `relation` are what they were. Each
answer of the table 3 of 3 on a jump, and one to three times on a child's
link, a type's link and a tag's attachment, which answered the same; every
patch sent to a link of its own. Measured on 15.0.640, 2026-10-13, with a
contract test. No tool sends a link's `kind`, and `links.update()` has no field
for it.

```
Attach a tag:  POST /api/links/{brainId}
               { "thoughtIdA": <thought>, "thoughtIdB": <tag, kind=4>, "relation": 2 }
               -> the server creates relation=1, meaning=5

Detach:        DELETE /api/links/{brainId}/{linkId}
Read:          graph.tags   (the tag does not appear in parents, but on a tag: L44)
Create:        POST /api/thoughts/{brainId}  { "name": ..., "kind": 4 }
               -> the identifier of a tag already named so, if there is one (L39)
```

`relation: 2` against a thought with `kind=1` produces an ordinary parent — it is
the target's `kind=4` that flips the behaviour, not the `relation` value.

**Visibility delay of 0.1–0.5 s.** Immediately after the `POST`, the graph returns
a stale tag list; three tags attached in a row all appeared only after ~1 s.
Detachment shows up after ~0.5 s. This is not the five-second refresh of the
search's index (L34) — it is a different mechanism.

`statistics.links` does not count links with `meaning=5`.

### Enumerating all thoughts through the log — not enough on its own

There is no "list all thoughts" endpoint and no traversal beyond one hop. But
`/api/brains/{id}/modifications` with no date range returns the history up to
`maxLogs` entries (when there are more, it keeps the newest and returns them
newest first; the rest is reached by paging back on `endTime`, L14), and
replaying `modType 101` (created) minus `modType 102` (deleted) over the whole
log reconstructs the current population.

Cross-checked against an independent source — an exact match:

| | log | `statistics` |
|---|---|---|
| `kind=1` (ordinary) | 38 | `thoughts` = 38 |
| `kind=2` (types) | 5 | `thoughtTypes` = 5 |

Note that `statistics.thoughts` counts **only** `kind=1`; types and tags are
separate fields. A discrepancy with the log by exactly that amount is expected,
not an error.

> **Correction.** The exact match above was on a brain whose thoughts were all
> created in it. Imported and old brains log far fewer `created` events than
> they hold thoughts: on a live TheBrain 15, 0 of 56, 1 of 44 and 125 of 187. A
> rebuild therefore takes the union of the log and a breadth-first walk over
> `graph`; see ARCHITECTURE.md §7. The walk relies on two graph facts, both
> contract-tested: a tag's graph lists the thoughts it marks as `children`, and
> a type's graph lists its instances there too.

The same log supplies the signals for incremental sync: `101` add, `102` remove,
`103` re-embed the name, `211` the aliases, `202` the label, `203` the type,
`801`/`802`/`803` the note. Mind L13 for the last group: those entries are keyed
by the note's attachment, and the thought is in `extraAId`. And L20: changes to a note with
nothing else logged between them, in any brain, are one `803`, which carries
the time of the last of them, so reading from a watermark still finds it. A tag has no thought
event at all (L18): it comes and goes as a link, so both ends of a link's
`101`/`102`/`402`/`404` are read again. And a `103` against a tag or a type also
marks the thoughts its graph lists as children, because the log does not. A
`304` marks the thought whose kind changed (L31): the index keeps the kind
beside the document, and a type reads with a label the log says nothing of.

### Error formats — there are five of them

```
400  "Could not retrieve list of Types for brain ..."   ← a bare JSON string
400  (no body)                                           ← a write with a malformed identifier in its path
401  Invalid API Key                                     ← plain text
401  API Key was not provided. (Using the 'Authorization' header)
401  "Access to brain <id> is unauthorized."             ← a bare JSON string: the brain, not the key
403  To use the TheBrain API, make requests to /api ...  ← plain text with no content type: the catch-all
404  {"type":"https://tools.ietf.org/html/rfc9110#...","title":"Not Found","status":404,"traceId":"..."}
404  "Source Thought <id> could not be located"          ← a bare JSON string
200  <!DOCTYPE html> ...                                 ← a routing miss
```

There is no single error envelope. Normalising in the HTTP layer is mandatory.
One status is not one meaning either: a 401 is the key or the brain, a 404
names what it did not find or does not, and the 403 names nothing (L3).

### What works as expected

- `POST /api/thoughts/{brainId}` with `{name, sourceThoughtId, relation:1, kind, acType}` → `{"id": "..."}`
- `PATCH` accepts a plain JSON Patch array: `[{"op":"replace","path":"/name","value":"..."}]`
  with `Content-Type: application/json-patch+json`. Works for `/foregroundColor` too
- `notes/update` replaces the whole note; `notes/append` concatenates **without a
  separator** (`"AAA"` + `"BBB"` → `"AAABBB"`) — add the newline yourself. Joined
  to a line that way, a code block loses its closing fence (L5)
- `GET /api/notes/{...}` on a thought with no note → 200 with `markdown: ""` and
  `modificationDateTime: "0001-01-01T00:00:00"` (the "no note" sentinel)
- `graph` on an isolated thought returns empty arrays and `type: null`, no error
- `app/state.tabs[]` lists every open brain with its active thought, not just the
  current one
- No races reproduced on rapid sequential writes (update followed immediately by
  append behaved correctly)
